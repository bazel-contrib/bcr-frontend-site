Bazel build of jemalloc

The Bazel build of jemalloc, published to the Bazel Central Registry as the jemalloc module, is maintained at https://github.com/sallustfire/jemalloc. Each bcr-<version> branch there is upstream's source for that jemalloc release plus the Bazel build. Report problems with the Bazel build and send changes to it there; problems in jemalloc itself belong upstream.

The upstream jemalloc build performs a number of feature detection steps in the configure script. Here the checks that ask the toolchain (functions and their signatures, MADV_* constants, builtins, attributes, atomics, type sizes and byte order) are copies of configure.ac's test programs, compiled or linked by rules_cc_autoconf with the target's toolchain. configure's host table is expressed as platform selects. What configure learns by running a program on the build machine (page size, virtual address bits, huge page size) is set by flags under //settings/platform, and lg_page and lg_vaddr have per-platform defaults. Whether the CPU has rdtscp, which configure also learns by running a program, is a platform select; see JEMALLOC_HAVE_RDTSCP below.

Usage

See the examples/host_toolchain/BUILD.bazel file for examples of how to consume @jemalloc.

Notes

  • //settings/flags:jemalloc_prefix (--with-jemalloc-prefix): As in the make build, this defaults to "je_" on macOS and Windows and to no prefix elsewhere. On macOS jemalloc replaces malloc by overlaying the default malloc zone rather than by exporting malloc, free and so on; see //settings/flags:enable_zone_allocator below. A prefix renames the public API, malloc_conf, /etc/malloc.conf and MALLOC_CONF as INSTALL.md's --with-jemalloc-prefix describes. To call the API by its je_* names (je_mallctl, je_mallocx, ...) under any prefix, define JEMALLOC_NO_DEMANGLE before including jemalloc/jemalloc.h. Set the flag, or jemalloc()'s jemalloc_prefix, to choose a prefix explicitly. The flag defaults to "auto", which jemalloc resolves for the target platform, so a select() on the flag sees "auto", and the flag provides no $(JEMALLOC_PREFIX). Set the prefix explicitly where a consumer needs to know it.
  • //settings/flags:enable_zone_allocator (--disable-zone-allocator): As in the make build, this is on for Darwin and off elsewhere, and turning it on for any other platform fails the build. With it on, jemalloc registers a malloc zone from a constructor in src/zone.c, so plain malloc reaches jemalloc in every binary that links @jemalloc, statically or not; this includes binaries that call jemalloc only through a prefixed API. Turn it off to keep jemalloc private to that API. Unlike the make build's static libjemalloc.a, the library links with -u
  • //settings/flags:enable_debug (--enable-debug): Turns on jemalloc debug (JEMALLOC_DEBUG). Defaults to "auto", which follows the compilation mode and defines it in -c dbg builds only; "yes" and "no" set it in any compilation mode. configure's --enable-debug also turns off its optimization flags; here the compilation mode alone decides optimization. jemalloc debug includes the checks of //settings/flags:enable_opt_safety_checks (--enable-opt-safety-checks), //settings/flags:enable_opt_size_checks (--enable-opt-size-checks) and //settings/flags:enable_uaf_detection (--enable-uaf-detection), which, off by default, turn them on without the rest of debug. Set to False, they do not turn off the checks debug includes. jemalloc()'s debug, opt_safety_checks, opt_size_checks and uaf_detection set them per target.
  • Library targets: @jemalloc//:jemalloc is the cc_library to depend on, through deps or the malloc attribute. It builds libjemalloc.a and no shared library of its own (linkstatic). Each jemalloc() target is a library of its own, built with its attributes' settings.
  • //settings/flags:nm (NM): The nm that lists the library's symbols for private_namespace.h, as configure's NM does. Unset, it is the C++ toolchain's nm (CcToolchainInfo.nm_executable). rules_cc's rule-based toolchains supply that only through a cc_legacy_tool, so with one that declares none, such as the hermetic LLVM toolchain (the llvm module), the build fails at that step until this is set to an nm target, for example --@jemalloc//settings/flags:nm=@llvm//tools:llvm-nm, as examples/hermetic_llvm does. MSVC-compatible toolchains declare no nm, so with msvc-cl the symbols are listed by the toolchain's linker as link /DUMP /SYMBOLS, which is dumpbin, and with clang-cl by the llvm-nm.exe beside its clang-cl.exe.
  • //settings/platform:lg_vaddr (--with-lg-vaddr): Defaults as configure does: 48 on aarch64, 57 on x86_64 (the configure script's cross compilation value; a native configure runs CPUID instead, which gives 48 on a CPU without 5-level paging), and the pointer width on any other CPU whose width @platforms makes clear. Any other CPU, such as ppc, must set it, or the build fails. Set it explicitly to override. The flag defaults to "auto", which jemalloc resolves for the target platform, so a select() on the flag sees "auto". Any value is written into the header as is, without checking that it is a number.
  • //settings/platform:lg_page (--with-lg-page): Defaults to 16 (64 KiB) on aarch64 Linux and Android and on ppc64le Linux, so one build runs on kernels with 4K, 16K or 64K pages, at the cost of a coarser page granularity on 4K kernels (configure's cross compilation value is 12, which fails at startup on a 16K or 64K kernel). Darwin defaults to 14 and everything else to 12. Set it explicitly to override.
  • //settings/platform:lg_hugepage (--with-lg-hugepage): Defaults to 21 (2 MiB), configure's value when it cannot read the huge page size. It must be at least lg_page, as configure requires, or the build fails; so on aarch64 Linux and Android and ppc64le Linux, where lg_page defaults to 16, a value below 16 needs lg_page set explicitly too.
  • JEMALLOC_HAVE_RDTSCP (no configure option): Defined on x86_64 Apple targets and nowhere else, with no flag to change it. There percpu_arena needs it: malloc_getcpu reads it only where neither _WIN32 nor sched_getcpu applies, and without it percpu_arena reaches not_reached(). A native configure on an Intel Mac whose CPU has rdtscp defines it; a cross build or --with-lg-vaddr leaves it undefined, as this build does on every other target, where leaving it out has no effect. On an x86_64 CPU without rdtscp (Intel's before Nehalem, AMD K8 before revision F, the Bonnell and Saltwell Atoms), percpu_arena, which is off by default, reaches an illegal instruction instead.
  • glibc: Without a prefix, the _libc* functions and __posix_memalign are probed and listed (exempt from private renaming) wherever they link, and on Linux the hooks __malloc_hook, __realloc_hook, __free_hook and __memalign_hook where they still link (glibc before 2.34), exactly as configure does. jemalloc defines the hooks, and aliases the _libc* functions and __posix_memalign, only where the malloc hooks link on glibc; elsewhere, as with configure, these names are listed but not defined.
  • //settings/flags:enable_user_config (--disable-user-config): On by default, as in the make build: jemalloc reads options from the MALLOC_CONF environment variable and the /etc/malloc.conf link, both renamed by a prefix. Set it to False, or jemalloc()'s user_config to "False", to read neither, leaving the options compiled in through //settings/flags:malloc_conf and an application's own malloc_conf.
  • //settings/flags:enable_dss (--disable-dss): On by default: as in the make build, jemalloc can allocate from the data segment with sbrk(2) wherever the target links sbrk and does not deprecate it (every Apple OS does). Set it to False, or jemalloc()'s dss to "False", to never call sbrk, as when something else in the process owns the data segment.
  • //settings/flags:enable_pageid (--enable-pageid): Off by default. On, jemalloc names its anonymous mappings (jemalloc_pg, or jemalloc_pg_overcommit) in /proc/
  • //settings/flags:enable_force_getenv (--enable-force-getenv): Off by default, so jemalloc reads MALLOC_CONF with secure_getenv, or ignores it in a setuid or setgid process where only issetugid is available. On, it always reads it with getenv, including in privileged processes. jemalloc()'s force_getenv sets it per target.
  • //settings/flags:enable_experimental_sdt (--enable-experimental-sdt): Off by default. On, jemalloc emits USDT probes: systemtap's, where the toolchain links configure's <sys/sdt.h> program (a nested function, so GCC only), or else jemalloc's own on Linux x86_64, aarch64 and 32-bit Arm and on Android aarch64 and x86_64. As with configure, any other Linux or Android CPU gets no probes and no error, and any other platform fails the build. jemalloc()'s experimental_sdt sets it per target.
  • //settings/flags:experimental_sys_process_madvise (--with-experimental-sys-process-madvise): Empty by default. jemalloc uses process_madvise (for batched purging, which opt.process_madvise_max_batch enables) where the C library's headers declare SYS_process_madvise and PIDFD_SELF. Set it to the system call number, for example 440, to use it on a Linux target whose headers lack them, as configure does wherever its probe fails and madvise links. The value is written into the header as is. Unlike configure, the build also writes EXPERIMENTAL_SYS_PROCESS_MADVISE_NR where the probe passes or madvise is missing, where nothing reads it.
  • //settings/flags:enable_prof (--enable-prof): "no" by default. "libunwind", "libgcc" and "gcc" choose configure's backtrace methods; "frame_pointer" is --enable-prof-frameptr, which compiles jemalloc with -fno-omit-frame-pointer. musl has no <execinfo.h>, so frame_pointer does not build there, as with configure. configure offers frame_pointer only on Linux with a GCC-compatible compiler and silently picks another method elsewhere; here any other platform or compiler fails the build.
  • --enable-tsan, --enable-ubsan and --with-cxx-stdlib: configure's sanitizer options only add -fsanitize=thread or -fsanitize=undefined to the compile and link flags, and --with-cxx-stdlib only chooses -lstdc++ or -lc++. Here the C and C++ toolchain owns both, so there are no flags for them: enable a sanitizer through the toolchain's features or --copt and --linkopt, and choose the C++ standard library with the C++ toolchain.

Settings whose "auto" default jemalloc resolves for the target platform:

  • //settings/flags:enable_cxx (by the C++ compiler: off for cl and clang-cl)
  • //settings/flags:enable_lazy_lock
  • //settings/flags:enable_zone_allocator
  • //settings/flags:jemalloc_prefix
  • //settings/platform:lg_page
  • //settings/platform:lg_vaddr

The optional public functions (memalign, valloc, pvalloc, malloc_size) are exported exactly where configure would export them: where the target's toolchain links them, as the configured headers record.

Fidelity with upstream

The upstream build generates several headers with shell, awk and sed scripts, run by configure and make on the host. Here Bazel generates them with small C++ tools, so a module that depends on @jemalloc needs only its C and C++ toolchain: no host shell, awk or sed. As in configure, the public symbols include optional functions only where the configured headers define the matching macro, so the headers built from them are written when the build runs. private_namespace.h comes from listing the library's symbols with the toolchain's nm, or with dumpbin for MSVC, as upstream's private_symbols.awk reads both. From dumpbin it also renames two kinds of external definition that awk skips: symbols in a section whose hex number begins with a letter, and communal symbols, which nm lists as C and awk accepts there. Those are what cl's private_namespace.h adds to upstream's, so its fidelity tests use listings without them.

The upstream scripts are kept, not replaced. Each generated header has a fidelity_test in tools/fidelity that runs the unmodified upstream script, as configure.ac invokes it, on the same inputs and with the same settings, and fails if the outputs differ. The scripts run with hermetic gawk, grep, sed and coreutils, which are dev dependencies: they are fetched for this repository's tests and never for consumers. The upstream-oracle CI job goes further, building the upstream release with configure and make and comparing every script-generated header, and the public and wrapped symbol lists, with the Bazel build's.

When upgrading jemalloc, a failing fidelity test means an upstream script changed and its Bazel counterpart must follow.

Validated Platforms

Tested in CI with the latest Bazel 7.x, 8.x and 9.x:

  • Ubuntu 22.04, 24.04 & 26.04 (x86_64)
  • Ubuntu 24.04 (aarch64)
  • MacOS 15 & 26 (arm64)

The minimum supported Bazel, 7.4.0, is tested on Ubuntu 24.04 (x86_64), on Windows Server 2025 with MSVC and, for the host toolchain examples only, MacOS 15. Windows Server 2025 (x86_64) is tested with MSVC (msvc-cl), host toolchain examples included, on the latest Bazel 7.x, 8.x and 9.x, and with clang-cl on the latest 9.x, without the fidelity checks, whose gawk, grep and sed dev dependencies do not build for Windows. Profiling (--config=prof-*) is tested on Linux only. Debug is tested with prof-libgcc, log on and cache oblivious off, on Ubuntu 24.04 (x86_64) with the latest Bazel 9.x only. The host toolchain examples build a jemalloc() target with debug on every tested platform.

Known Issues

  • Windows:
    • MinGW-w64 builds are cross-compiled in CI with hermetic LLVM, from Linux and macOS, but their programs are not run. MSYS2's mingw-gcc is not built in CI.
    • jemalloc 5.3's C++ support (operator new/delete) needs libstdc++ or libc++, so with cl and clang-cl //settings/flags:enable_cxx's __auto__ default turns it off, and a program's operator new and delete use the C runtime's allocator. Setting it to True with them fails analysis. Configure drops C++ for cl silently, even when asked for. Upstream's 5.4.0 removes both obstacles.
    • With cl and clang-cl, @jemalloc is a static library only: its API is declared with an empty JEMALLOC_EXPORT, so a DLL made from it with cc_shared_library exports none of it.
  • FreeBSD: configure's FreeBSD settings are translated (lazy lock, the vm.overcommit sysctl, -D_BSD_SOURCE for probes), but nothing has been built on FreeBSD.

How the registry entry is produced

The registry entry does not fetch the repository above. It fetches upstream's release tarball (for 5.3.1, jemalloc-5.3.1.tar.bz2 from jemalloc's GitHub releases) and adds the Bazel build to it:

  • overlay/ holds every committed file the tarball lacks: the BUILD and .bzl files, MODULE.bazel, settings/, tools/, examples/ and this README. The repository's own tooling, listed in .bcr/fork_only.txt, stays out.
  • patches/ holds one patch for each upstream file the repository edits, the difference between the committed file and the tarball's (except root dotfiles listed in .bcr/fork_only.txt, which ship as upstream's). Where a release's tarball ships files the build must not see, a branch adds .bcr/tarball_removals.txt, and patches/ also holds tarball_removals.patch, which deletes the files it lists. The exporter generates it from the tarball's own bytes, and each listed file must be one the repository does not commit.

The registry serves every tarball file the entry does not delete, so each one must be accounted for: committed by the repository, listed for removal, or listed in .bcr/release_generated.txt as a file upstream's release process generates and the repository does not commit, which ships as the tarball has it. Deleting or renaming an upstream file therefore takes a list entry too, or the export stops; both lists must name only tarball files the repository does not commit.

.github/scripts/export_bcr_entry.py writes the entry into a registry checkout from a committed ref. It writes nothing unless the tarball, overlay and patches, with the patches applied by GNU patch, rebuild the tree that ref defines, file for file, byte for byte and mode for mode. It builds that tree from the ref, not from the tarball: the ref's content for each file it ships, plus the tarball's copy of each listed release-generated file and of each root dotfile listed in .bcr/fork_only.txt. The tooling in .bcr/fork_only.txt, including these lists, stays out. GNU patch stands in for Bazel's patcher only because the exporter restricts the patches, and the files they touch, to what Bazel's line-based patcher reproduces exactly: plain ASCII paths, comments that cannot read as patch syntax, UTF-8 text without CR that ends in a newline, and deletions only of non-empty text files. A patch carries contents only, so the export also stops if the ref commits an upstream file as a symlink or with another executable bit. It stops, too, if an entry already in the registry for the same upstream release fetches a different tarball, so a re-rolled upstream asset cannot slip into a new .bcr.N. .bcr/presubmit.yml becomes the entry's presubmit.

Contributing

Send changes as pull requests to https://github.com/sallustfire/jemalloc, against the branch for the jemalloc version, such as bcr-5.3.1. Support for a new jemalloc release starts as a new bcr-<version> branch.

  • Leave upstream's files as upstream ships them where you can. Each edit to one ships to the registry as a patch, so edit one only when the Bazel build needs it, and say why in a comment beside the edit.
  • A new file ships in the overlay with no further step. List it in .bcr/fork_only.txt only if it is tooling for this repository, such as CI configuration.
  • Run bazel test //... at the root and in examples/host_toolchain and examples/hermetic_llvm. CI runs them on the platforms above and builds the upstream release with configure and make to compare.

A release sets version in MODULE.bazel to <upstream> for the first entry of an upstream release, or to <upstream>.bcr.<N> for a later revision of the Bazel build on the same release, runs .github/scripts/export_bcr_entry.py --registry <registry checkout>, and opens a pull request against the Bazel Central Registry with the entry it writes.
