README

protoc-gen-clojure

A protoc and buf codegen plugin that emits Clojure, with first-class support for Protobuf Edition 2024.

Generated code is a defrecord per message plus straight-line ->proto / proto-> functions built on FieldDescriptors resolved once at load time — the shape is known at codegen time, so the representation is too. Services come out as descriptors ready for a Clojure gRPC runtime.

;; Generated by protoc-gen-clojure from acme/greeter/greeter.proto. Do not edit.
(ns acme.greeter.greeter
  (:require [clj-grpc.codec :as codec]
            [clj-grpc.runtime :as rt]
            [clj-grpc.runtime.service :as rts]))

(defrecord HelloRequest [name])
(defn HelloRequest->proto ...)
(defn proto->HelloRequest ...)
(def Greeter (rts/service file-descriptor "Greeter"))

Editions

The reason most third-party plugins break on a new edition is a hardcoded maximum. This one probes instead: it asks the linked protobuf-java which editions it can actually resolve by building a trivial descriptor at each candidate, and advertises the highest that succeeds. Bumping the protobuf-java dependency raises the ceiling on its own.

It also performs no feature resolution of its own. The emitted file embeds the FileDescriptorProto verbatim and lets protobuf-java resolve edition features at load time, so a future edition needs no codegen change at all.

Enum membership is not evidence of support: protobuf-java 4.35.1 lists EDITION_2026 long before it can resolve it, so that value is probed and declined rather than advertised.

Install

Download a binary for your platform from Releases and put it on PATH. The file name matters — protoc discovers plugins as protoc-gen-<name>, and that is what makes --clojure_out work:

VERSION=0.3.0
curl -fsSLo protoc-gen-clojure \
  "https://github.com/bpalermo/protoc-gen-clojure/releases/download/v$VERSION/protoc-gen-clojure_${VERSION}_linux_x86_64"
chmod +x protoc-gen-clojure && mv protoc-gen-clojure /usr/local/bin/

linux_x86_64 is fully static — no libc dependency at all, so it runs on any distribution, including Alpine and a scratch container.

linux_aarch64 is dynamically linked and carries a glibc floor of 2.34, so a distribution older than roughly Debian 12 or Ubuntu 22.04 will reject it with GLIBC_2.xx not found. The release asserts that floor so it cannot drift unnoticed.

The asymmetry is not a preference. GraalVM's --libc=musl demands x86_64-linux-musl-gcc even when running on arm64 with the aarch64 compiler on PATH, so it hardcodes the x64 triple and an arm64 static binary cannot be produced at all (issue #17).

On macOS, a binary downloaded from the internet carries a quarantine attribute and will be killed on first run. Clear it:

xattr -d com.apple.quarantine /usr/local/bin/protoc-gen-clojure

Binaries are unsigned and un-notarized for now.

Use

protoc

protoc --clojure_out=src/gen hello.proto

buf

A local: plugin, no registry involved:

# buf.gen.yaml
version: v2
plugins:
  - local: protoc-gen-clojure
    out: src/gen

A container image is published to ghcr.io/bpalermo/protoc-gen-clojure, tagged with the version, the commit, and latest:

docker run --rm -i ghcr.io/bpalermo/protoc-gen-clojure < request.bin > response.bin

Remote execution on the BSR is prepared but not published — public plugin publishing there is not self-serve. See buf.plugin.yaml.

Bazel

New to Bazel? Start at bazel.build — this section assumes a bzlmod project (MODULE.bazel), which is the default from Bazel 7 on.

Consumers need no Clojure, no JVM and no GraalVM: the toolchain fetches a prebuilt native binary for the host platform.

# MODULE.bazel
bazel_dep(name = "protoc_gen_clojure", version = "0.3.0")

plugin = use_extension("@protoc_gen_clojure//clojure:extensions.bzl", "toolchains")
use_repo(plugin, "protoc_gen_clojure_toolchains")

register_toolchains("@protoc_gen_clojure_toolchains//:all")
# BUILD.bazel
load("@protoc_gen_clojure//clojure:defs.bzl", "clojure_proto_library")

clojure_proto_library(
    name = "hello_clj",
    outs = ["example/hello.clj"],
    proto = ":hello_proto",
)

A complete, working example is in examples/bzlmod — which is also the module BCR runs against on every release. Full attribute reference for every public symbol is in docs/, generated from the Starlark docstrings: clojure_proto_library, the toolchain, the module extension.

clojure_proto_library is a real Starlark rule rather than a genrule for a specific reason: protoc must be able to resolve every transitive import, and the only way to give it them is --descriptor_set_in with the transitive descriptor sets. Those live on ProtoInfo, which a genrule cannot reach. (--proto_path is not an alternative: edition 2024's import option java_features.proto is exported in no protobuf filegroup.)

Options

Comma-separated, as --clojure_out=key=value,key2=value2:DIR, or via clojure_proto_library's options attribute:

option meaning
ns_prefix=foo prefix every generated namespace with foo.
keep_source_info=true embed SourceCodeInfo (comments and spans). Off by default: it dominates the payload and is useless at runtime.
codec_ns=… namespace providing set-field! / get-field. Default clj-grpc.codec.
runtime_ns=… namespace providing file-descriptor / message / field. Default clj-grpc.runtime.
service_ns=… namespace providing service / methods-map. Default clj-grpc.runtime.service.

The three *_ns options exist because the requires in generated code are this plugin's real public API. They are written into every emitted file, so a project with generated code checked in is coupled to those names. Overriding them lets a project point at a differently named runtime without waiting on a plugin release.

Only service_ns pulls a gRPC runtime onto the classpath; a file declaring no service never requires it. So message-only consumers already avoid gRPC — the options are about naming, not about dependency weight.

Limitations

  • Nested messages get no record yet (issue #2). The enclosing message still round-trips; only the convenience record and conversion functions are missing, and the generated file names what was skipped so it is not a silent gap.
  • No Windows binaries.
  • BSR remote execution is prepared but unpublished.

Development

Bazel 8 and 9 are both supported — CI runs 8.6.0 and 9.2.0, and the BCR entry is tested on both. .bazelversion (9.2.0) sets the local development default. The rules load ProtoInfo from @protobuf — Bazel 9 removed it from the Starlark globals, and the module load path works identically on 8.

bazel test //...                      # everything, lint included
bazel test //... --test_tag_filters=lint   # just lint: buf, shellcheck, formatting
bazel run //bazel/dev:format          # FIX formatting (buf format, buildifier)
bazel run //test:update_golden        # after an intended codegen change

# The native binary is a Bazel artifact, and this runs it under real protoc and
# buf — both hermetic — in a scratch directory with only the plugin on PATH.
bazel build //src/protoc_gen_clojure:protoc_gen_clojure
bazel test  //test:distribution_test

# The same check against an arbitrary binary, e.g. a downloaded release asset:
PLUGIN=/path/to/protoc-gen-clojure bazel run //test:distribution_check

Emission is pinned by golden files under test/golden. A change to the emitter shows up as a diff there, and that diff is the change — review it.

Lint runs as ordinary Bazel tests, so bazel test //... fails on a lint error and CI needs no separate lint job. bazel run //bazel/dev:format fixes what is mechanically fixable — buf for protos, buildifier for Starlark. Every tool is hermetic and pinned by MODULE.bazel: buf lints with the same 1.72.0 the distribution test verifies with.

Shell is linted but not formatted. shfmt is only reachable through @multitool, and registering that hub needs a non-dev use_extension on a dev-only module, which makes @rules_multitool invisible to consumers and breaks them at module resolution. shellcheck is unaffected — rules_lint aliases it inside its own repo.

shellcheck is not decoration here: SC2318 catches exactly the bug this repo already shipped — local dir="$1" out="$dir/x", where bash expands every word of a local before performing any of its assignments, so the script died under set -u.

Whether the generated code actually works — round-trips on the wire, serves real RPCs, stays byte-identical to protoc's Java backend — is asserted by the runtime library the generated code requires, which owns those tests. That is what lets this module depend on nothing but protobuf-java.

The native binary is built by rules_clj's clj_native_binary rather than rules_graalvm's rule — which crashes Bazel on macOS by setting SDKROOT twice (once itself via apple_support, once via Bazel's own Xcode env provider). The rule is honest about its one compromise: the action is local and unsandboxed with the ambient environment, because native-image shells out to the platform linker.

Windows binaries are not built yet.
